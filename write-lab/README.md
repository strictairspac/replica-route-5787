# 写入一致性演练场（write-lab）

针对一个具体交接难题的可交互演练：**写完没收到回执、又赶上主库下线，这笔账到底怎么查清？**
纯前端、零后端依赖，双击 `index.html` 即可在浏览器打开；同一个 seed 与动作序列可以逐字节确定性重放。

> 这是 Raft 风格的受控模型，不连接真实数据库。日志位点是命名谱系内的单调整数，
> 网络是带固定时延的虚拟消息队列，故障与丢消息都是人工布控的确定性事件。

## 要回答的四个问题，以及本模型的答案

| 问题 | 模型里的机制 | 页面上看哪里 |
|---|---|---|
| 同笔写入重试不能重复生效 | 写号（客户端幂等令牌）一次绑定内容；客户端、主库日志、状态机三处查重，同号同内容只命中旧条目 | 台账「同号重试」按钮 + 日志长度不变 |
| 同号换内容要拒绝 | 三处防线：客户端直接拦截；主库发现写号已绑定不同值回 `CONFLICT`；状态机二次兜底 | 「同号换内容」按钮 → 红色冲突拒绝，原值不动 |
| 换主后已确认写入不能丢 | 只有多数派（N/2+1）落盘才算确认；选举按「日志末尾 term+index 够新」拒票，落后副本无法当选 | 节点日志/提交/应用位点 + 换主后新主状态机 |
| 副本没追齐时非关键写入还能继续 | 非关键写主库本地落盘即回执（`LOCAL_ACKED`），明确标注不经久；换主时未进多数派的条目标 `LOST` 而不是静默成功 | 剧本④，台账「集群事实」列 |

### 关键设计：集群事实 与 客户端证据 是两层

- `quorumAcked`：集群事实——这笔写是否已进多数派日志，与客户端无关。
- `status`：客户端拿到了什么证据。回执被丢时，**集群早已安全落盘，但台账仍停在「待确认」**。
- 此时唯一正确动作是用写号「查明结果」或同号同内容重试；**严禁换新号重写**（会造成双花/重复入账）。
- 查明返回 `COMMITTED` 才补回客户端证据，全过程不产生第二条日志。

### 何时确认、证据没到怎么办（策略取舍由本演练显式承担）

- **关键写**：多数派票到齐才发确认回执。代价 = 写入等待（至少一个复制 RTT）+ 无多数派时直接不可用（请求被挡，保持待确认）。
- **非关键写**：主库本地落盘即回执，分区/副本落后时业务不中断。代价 = 旧主在复制完成前崩溃时，该确认会丢，台账如实标 `LOST`。
- **证据没到**：不猜测成功、不换号。待确认 → 查明 → 已确认则补证据；查无实据且旧主已失势，才允许同号重试。
- 页面右栏「代价与状态」量化：累计无主不可用 ms（换主代价）、换主次数、被丢弃消息数、虚拟时钟（等待代价）。

## 页面能做什么

- **排写入**：写号/键/值/会话，区分关键写与非关键写；可开「超时自动同号重试」。
- **丢回执**：一键布控丢弃下一条客户端回执；也可对任意节点间链路布控丢单条消息或完全隔离。
- **同步**：「立即同步」只投递在途消息（不跑选举定时器）；「推进到稳定」驱动心跳与选举收敛。
- **换主**：节点下线/恢复/手动参选；顶部与时间线显示选举、拒票理由（日志落后）、本次不可用时长。
- **看待确认的写如何查明**：写入台账每行可同号重试、查明结果、同号换内容（演示拒绝）、按会话读该键。
- **同一会话随后读到什么**：主库读为线性一致；指定副本读会检查「本会话已确认写号是否都已应用」，滞后时明确列出缺失写号，而不是默默返回旧值。
- **旧试验回看**：保存试验到 localStorage（含完整动作序列与校验和），随时一键重放，校验和一致即证明可复现。

### 六个预置剧本

1. 写完没收到回执，怎么查清（丢回执 → 待确认 → 查明补证据 → 重试幂等）
2. 同号换内容必须拒绝
3. 主库下线换主，已确认写入不丢
4. 副本没追齐：非关键写继续，但换主会丢；关键写被挡
5. 无多数派：写入排队待确认，恢复后同号重试成功
6. 同会话读己之写：滞后副本读什么

## 文件

| 文件 | 职责 |
|---|---|
| `engine.js` | 确定性模拟引擎（UMD，零依赖）：虚拟时钟、消息队列、Raft 风格选举/复制/提交、幂等与冲突三道防线、读写与查询 |
| `app.js` | 页面控制器：渲染拓扑/台账/时间线/链路/历史，绑定全部交互，localStorage 持久化 |
| `index.html` / `styles.css` | 三栏控制台布局 |
| `engine.test.cjs` | 12 条引擎安全性质测试（Node 内置 test runner，零依赖） |
| `dom.smoke.test.cjs` | 9 条真实 DOM 冒烟测试（jsdom）：六个剧本、手动操作、历史回看校验和 |

## 模型边界（不假装的部分）

- 不模拟真实网络抖动：时延与丢包都是显式布控，同一 seed 结果完全确定。
- 不实现完整 GTID 集合、成员变更、快照压缩与日志压缩；单组 3/5 节点。
- 不模拟拜占庭故障：节点要么按协议工作，要么下线/被隔离。
- 选举超时的随机抖动来自可播种的 PRNG（mulberry32），这是唯一的「随机」来源，重放一致。
- 本地回执（非关键写）是教学用的显式降级档位，不是真实产品的默认配置；真实系统通常配合去重表/对账兜底。

## 脑裂与选举的额外保证

- 主库每次心跳自检：一旦发现自己的心跳已送达不到多数派，立即主动退位，不再以主库自居，避免双主。
- 候选者参选前自检：联系不到多数派的失联节点不自增 term、不发起必败选举，只安静等待链路恢复，因此不会出现选举风暴。
- 投票按日志新旧判定：日志落后于多数派的旧节点即使反复参选也会被拒票，只有包含全部已确认条目的节点能当选——这是「换主不丢数据」的最后一道闸门。
- 链路恢复时在任主库立即补一次心跳，把分区期的旧候选者在下次选举超时前拉回 follower，term 快速重新一致。
